Проектирование синхронизации через Google Диск

Дата записи. 2026-11-17.
Опирается на решения 4 и 5, модель данных и проверку входа через Google на мини-приложении. Конфликты и формат файлов закреплены решением 11.

Что должно получиться

1. Запись с телефона появляется на компьютере и наоборот.
2. Своего сервера нет. Всё хранится в скрытой папке приложения на личном Google Диске пользователя.
3. Ничего не теряется, даже если одну запись правили на двух устройствах без сети.
4. Диск видит только шифр.
5. Без синхронизации приложение работает полностью, как сейчас.

Чего в первой версии нет. Синхронизации при закрытом приложении, смены пароля шифрования, совместной работы нескольких людей, слияния текста по словам.

Главные решения

1. На Диске файлы только создаются и удаляются, но не переписываются. Два устройства никогда не пишут в один файл, поэтому нет гонки записи.
2. Передаём состояния объектов, а не отдельные действия. В файле лежит запись целиком в том виде, какой она стала. Повторная отправка безопасна, а потерянные промежуточные шаги ничего не ломают.
3. Отдельную таблицу журнала не заводим. У каждого объекта уже есть номер правки rev. На устройстве для каждого объекта запоминается syncedRev, то есть номер правки, который уже согласован с Диском. Если rev больше syncedRev, объект ждёт отправки. Таблица changes из модели данных не нужна.
4. Порядок событий решают номера правок, а не часы. Часы телефона бывают неверными. Время используется только для ничьей при конфликте.
5. Конфликт решается сам и без вопросов. Побеждает правка, сделанная позже. Проигравшая версия сохраняется копией. Если нужна одна из них, пользователь удаляет другую обычным удалением.
6. Ключ шифрования один на всё хранилище и вычисляется один раз за сеанс. Соль лежит один раз в открытом файле meta.json. Так не нужно считать 600 000 кругов для каждого файла (параметры в docs/encryption-design.txt).
7. Данные сначала сжимаются, потом шифруются. Шифр не сжимается, а текст сжимается в несколько раз.
8. Движок синхронизации общается с хранилищем через маленький интерфейс: показать список файлов, прочитать, создать, удалить. В решении 4 были первые три действия, удаление нужно для сжатия старых файлов. Благодаря интерфейсу движок проверяется без Google.

Что лежит на Диске

Все файлы в папке appDataFolder, доступ по разрешению drive.appdata.

1. meta.json. Открытый файл. Версия формата, соль 16 байт, число кругов PBKDF2, проверочная строка (шифр известной фразы). По ней при вводе пароля понятно, верный он или нет. Секретов в файле нет.
2. seg-ИДУСТРОЙСТВА-НОМЕР.sb. Сегмент. Объекты, которые это устройство изменило с прошлой отправки. Номер растёт на единицу, пишется шестью цифрами. Не больше 500 объектов в сегменте.
3. snap-ВРЕМЯ-ИДУСТРОЙСТВА.sb. Снимок. Полное состояние всех объектов, включая удалённые, на момент создания.

Содержимое файла .sb. Текст JSON с полями v (версия формата, сейчас 1), iv (вектор 12 байт) и data. В data лежит результат AES-GCM над сжатым gzip текстом полезной нагрузки. В дополнительные данные шифра входят вид файла, идентификатор устройства и номер, поэтому файл нельзя выдать за другой.

Полезная нагрузка сегмента. Поля kind равно segment, deviceId, counter, createdAt и список objects. Каждый элемент списка это entity (note, card, link, task или tag) и data, полное состояние объекта. Нагрузка снимка отличается видом snapshot и полем covers: для каждого устройства наибольший номер сегмента, который уже учтён в снимке.

Файл копии данных (экспорт) сделан отдельно и снимком не является: в нём только живые объекты, он не зашифрован, чтобы открываться вне приложения, и без служебных полей синхронизации. Проверки объектов при чтении файла (src/storage/backup.ts) можно использовать и при чтении файлов с Диска. Загруженные из копии объекты получают отметку «не синхронизировано» сами, потому что для них нет записи в syncState.

Диск видит имена файлов, их размер и время. Содержимое он не видит.

Что нового на устройстве

1. Хранилище syncState в Dexie, версия схемы 2. Ключ вроде note:ID, значение syncedRev.
2. Поле conflictOf у записи: id записи, копией которой эта запись стала при конфликте, или пусто.
3. Настройки только этого устройства: syncProvider, syncCursor (для каждого чужого устройства номер последнего прочитанного сегмента), syncCounter (номер последнего своего сегмента), syncLastAt (время последнего успешного круга), список применённых снимков.
4. Ключ шифрования запоминается на устройстве как неизвлекаемый, см. docs/encryption-design.txt. Движок получает уже готовый ключ.

Один круг синхронизации

Сначала получаем, потом отправляем. Тогда конфликт обнаруживается до отправки.

1. Проверить, что хранилище подключено, есть сеть и есть токен доступа. Нет токена и тихо получить новый не вышло: статус «нужен вход», круг закончен.
2. Получить список файлов папки.
3. Нет meta.json: это первое подключение, см. ниже.
4. Скачать то, чего ещё нет на устройстве: снимки, которые не применялись, и сегменты других устройств с номером больше курсора, по возрастанию номера.
5. Применить каждый объект по правилам из следующего раздела. Файл применяется одной транзакцией базы. Курсор сдвигается только после неё.
6. Собрать свои изменения: объекты, у которых rev больше syncedRev. Нет таких: перейти к шагу 8. Есть: разбить на сегменты по 500, дать номера счётчик плюс один, загрузить. Только после успешной загрузки записать syncedRev и новый счётчик.
7. Если неохваченных снимком сегментов больше 100, сделать снимок.
8. Записать время успеха и статус «синхронизировано».

Правила применения пришедшего объекта R к местному объекту L

1. Местного L нет. Записать R, syncedRev равен R.rev. Это относится и к удалённым объектам.
2. L есть, своих неотправленных правок нет (L.rev равен syncedRev), и R.rev больше L.rev. Заменить L на R, syncedRev равен R.rev.
3. Своих правок нет, и R.rev не больше L.rev. Пропустить. Это повтор или старое состояние.
4. Свои неотправленные правки есть (L.rev больше syncedRev), и R.rev не больше syncedRev. Пропустить, это старое состояние.
5. Свои неотправленные правки есть, и R.rev больше syncedRev. Объект правили на двух устройствах. Если содержимое одинаковое (не считая rev, deviceId и updatedAt, а два удаления считаются одинаковыми), принять R. Иначе это конфликт.

Конфликт

1. Победитель определяется так. Больше updatedAt. При равенстве больше rev. При равенстве больше deviceId как строка. Результат одинаков на всех устройствах без переговоров.
2. Побеждает местная версия. Она остаётся, но её rev становится максимумом из двух плюс один. Тогда на других устройствах она точно перекроет чужую. syncedRev не меняется, объект уйдёт в отправку.
3. Побеждает пришедшая. Записать её как есть, syncedRev равен R.rev.
4. Проигравшая живая версия сохраняется копией. Это новая запись с тем же текстом, временем события и createdAt, reviewedAt пусто, rev равен 1, conflictOf указывает на оригинал. Идентификатор копии получается из хеша строки «conflict:ID оригинала:устройство проигравшей:rev проигравшей» и приводится к виду UUID. Поэтому оба устройства создают копию с одним и тем же id и дублей нет. Копия уходит в отправку как обычная запись и попадает в неразобранные.
5. Если проиграло удаление, копии нет, правка просто осталась. Если проиграла правка, а победило удаление, копия правки создаётся, и текст не пропадает.
6. Что видит человек. Карточка копии подписана «Копия при конфликте» со ссылкой на оригинал. Он удаляет ненужную. Отдельного окна выбора нет.

Почему это сходится. Оба устройства применяют одну и ту же функцию к одной и той же паре версий, значит выбирают одного победителя и строят одну копию. Победитель получает номер правки выше обеих, поэтому его принимают все. Это проверяется отдельной проверкой на трёх устройствах со случайными правками.

Первое подключение, второе устройство, восстановление

1. Вход в Google, запрос разрешения drive.appdata.
2. Если meta.json нет: человек придумывает пароль, приложение предупреждает, что забытый пароль не восстановить, создаёт соль и ключ, пишет meta.json и загружает снимок со всеми местными данными.
3. Если meta.json есть: приложение просит пароль и проверяет его по проверочной строке. Неверный пароль: сообщение, ничего не меняется. Верный: обычный круг. Идентификаторы объектов это UUID, поэтому местные и скачанные объекты не совпадают и просто объединяются.
4. Пустое устройство получает всё из снимка и сегментов. Это и есть восстановление на новом устройстве. Если стёрты данные браузера, устройство теряет свой deviceId и становится новым. Старые файлы остаются на Диске и ничего не ломают.
5. Если два устройства одновременно создали meta.json, остаётся тот, что создан раньше (при равенстве файл с меньшим id). Лишний удаляет создавшее его устройство и берёт соль из оставшегося. Случай редкий, проверяется вручную.

Снимки и уборка

1. Когда делать снимок. Неохваченных сегментов больше 100 или последний снимок старше 30 дней при наличии новых сегментов.
2. Снимок собирается из полного состояния базы после получения чужих изменений. В covers записываются номера всех учтённых сегментов.
3. Покрытые снимком сегменты и прежние снимки удаляются не раньше, чем через 7 дней после создания нового снимка. За неделю другие устройства успеют забрать снимок, а одновременные снимки двух устройств не потеряют данные друг друга. Применение любого файла безопасно повторять, поэтому лишние файлы вреда не делают.
4. Устройство, которого не было больше недели, читает самый новый снимок целиком, а потом сегменты после него.
5. Удалённые объекты в снимках остаются навсегда. Иначе старое устройство, вернувшись, воскресило бы удалённую запись. Не решено, нужно ли через какое-то время стирать текст у давно удалённых записей, см. открытые вопросы.

Когда запускается синхронизация

1. Сразу после подключения.
2. При открытии приложения и при возврате к нему (событие visibilitychange).
3. Через 60 секунд после последней правки, чтобы не отправлять на каждую букву.
4. Когда вернулась сеть (событие online).
5. По кнопке «Синхронизировать» в настройках.

Одновременно идёт один круг. Внутри вкладки это флаг, между вкладками Web Locks API.

Честное ограничение. Установленное веб-приложение не умеет синхронизироваться в фоне при закрытом приложении. Periodic Background Sync есть не везде, и мы на него не рассчитываем. Поэтому чужие изменения приходят, когда приложение открыто.

Состояния для экрана

1. Не подключено.
2. Синхронизировано, с временем последнего успеха.
3. Идёт синхронизация.
4. Нет сети.
5. Нужен вход в Google.
6. Нужен пароль.
7. Ошибка с понятным текстом.
Рядом счётчик «ждёт отправки: N», это число объектов, у которых rev больше syncedRev.

Сбои и что не теряем

1. Обрыв при загрузке. syncedRev ещё не записан, следующий круг отправит то же самое. Получатель увидит повтор по номеру правки и пропустит.
2. Обрыв при чтении. Курсор сдвигается после применения файла, повтор безопасен.
3. Токен истёк. Тихо запросить новый, это работает, пока открыт сеанс Google. Не вышло: статус «нужен вход», правки копятся на устройстве.
4. Ответ Google 429 или 5xx. Повтор через 5, 30 и 120 секунд, потом до следующего запуска.
5. Файл не расшифровывается (повреждён или другой пароль). Пропустить, курсор за него не двигать, показать ошибку, ничего не удалять.
6. Диск заполнен. Показать ошибку, данные остаются на устройстве.
7. Версия формата файла новее, чем знает приложение. Не читать, показать «обновите приложение».
8. Неверные часы на телефоне. Порядок не страдает, затрагивается только выбор победителя при конфликте, а проигравшая версия сохраняется.
9. Кнопка «Отправить всё заново» делает снимок из местных данных. Нужна, если файлы на Диске удалили или повредили.

Безопасность

1. Токен Google хранится только в памяти страницы. В IndexedDB и localStorage его не пишем. После перезагрузки получаем заново.
2. Пароль и ключ на Диск не уходят.
3. Диск видит имена, размеры и время файлов, но не содержимое.
4. Подмену файла ловят дополнительные данные шифра. Если кто-то с доступом к Диску удалит файлы, данные на устройствах не пропадут, но на новое устройство они могут не попасть. Против этого кнопка «Отправить всё заново».
5. Запросить navigator.storage.persist() при подключении, чтобы браузер не стирал данные, если приложение долго не открывали.

Объекты с правилом уникальности

Для связи и для тега идентификатор строится из хеша ключа (владелец плюс карточка для связи, имя без учёта регистра для тега). Тогда одна и та же связь или тег, созданные на двух устройствах, окажутся одним объектом, а не двумя. Это делают карточки досье, правила слияния от этого не меняются.

Что проверяем

Автоматически (Vitest, без Google). Хранилище Диска заменяет версия в памяти. Два и три устройства это две и три базы в fake-indexeddb.
1. Каждое правило применения отдельной проверкой и три исхода конфликта.
2. Сходимость. Случайные цепочки правок, получений и отправок на трёх устройствах. В конце все базы равны, а текст каждой проигравшей версии есть в копиях. Начальные числа записываются, чтобы ошибку можно было повторить.
3. Повтор безопасен. Один и тот же файл применён дважды даёт тот же результат.
4. Обрыв после загрузки до записи syncedRev и повтор.
5. Новое устройство из снимка и сегментов получает то же состояние, что старые.
6. Копия при конфликте получает одинаковый id на обоих устройствах, дублей нет.
7. Файл не читается с чужим паролем и с подменённым именем.

Вручную (карточка проверки обмена между двумя устройствами). Телефон и компьютер. Запись туда и обратно. Правка одной записи на обоих устройствах без сети, потом сеть, должны получиться победитель и копия. Удаление. Режим самолёта. Второе устройство с нуля. Неверный пароль.

Что нужно изменить в слое хранения заранее. Сейчас база одна на весь модуль. Чтобы в проверках было две и три базы, нужна функция, создающая базу по имени. Это первый шаг реализации.

Порядок реализации по карточкам

1. Слой хранения: схема версии 2 (syncState и conflictOf), создание базы по имени. Карточка «Создать миграции данных».
2. Шифрование. Карточки «Спроектировать шифрование данных» и «Добавить шифрование данных».
3. Клиент Диска и интерфейс хранилища. Часть карточки «Реализовать синхронизацию через Google Диск».
4. Движок: круг, правила, снимки. Там же. Проверки пишутся вместе, а не после.
5. Разбор конфликтов: правило победителя, копии, подпись «Копия при конфликте». Карточка «Реализовать разбор конфликтов».
6. Состояния и кнопки. Карточки «Показывать состояние синхронизации» и «Сделать экран настроек».
7. Восстановление на новом устройстве.
8. Проверки синхронизации и конфликтов. Карточка «Написать проверки синхронизации и конфликтов».
9. Ручная проверка на двух устройствах.

Открытые вопросы

1. Не проверено тихое обновление токена после закрытия браузера и на телефоне. Если не работает, человеку придётся входить заново раз в сеанс. Проверить на мини-приложении до шага 3.
2. Статус приложения в Google Cloud. В режиме «Тестирование» войти могут только добавленные тестовые пользователи. Нужен ли перевод в «Опубликовано» и чего потребует Google, не выяснено.
3. Пороги 100 сегментов, 500 объектов, 60 секунд, 7 и 30 дней взяты как начальные. Уточнить замерами при реализации.
4. Стирать ли текст у давно удалённых записей, например через 30 дней, чтобы удалённое не жило вечно в шифре на Диске.
5. Андроид-версия (APK) входит в Google другим путём, см. решение 2. Движок от этого не меняется, меняется только получение токена.
